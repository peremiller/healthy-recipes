# Restaurant evidence and coverage limits

Current production does not have a live places provider configured. The default is a saved two-chain directory (McDonald’s and Denny’s), with menu evidence weighted heavily toward Denny’s. It cannot establish the best restaurant for a meal or that no other nearby restaurant serves it. Adding more hand-picked chains would still not make it comprehensive. Google area search alone is also insufficient: broad dish discovery and menu evidence for additional restaurants still need integration.

The UI discloses the two-chain menu limit prominently, reports unavailable live discovery, labels published schedules as not live-confirmed, and distinguishes source-page retrieval dates from merchant record update dates. One nearest branch per chain appears as a lead; other branches are grouped under the same chain rather than presented as extra choices. No random brand rotation or invented restaurant data is used.

The deployed API returns real restaurant names directly without a key or an upstream request. `server/data/official-restaurants.mjs` contains 812 public branch records from the [McDonald’s Philippines locator](https://www.mcdonalds.com.ph/store-locator) (805) and [Denny’s Philippines locations](https://www.dennys.ph/location) (7), retrieved November 7, 2026. It covers selected Philippine chains, not all nearby restaurants. These are nearby dining options; exact planned dishes and dietary suitability are not established.

McDonald’s coordinates and ordinary operating-hour descriptions come from its locator's embedded store records. Service badges such as “24 Hours” never supply missing hours. Of 805 records, 682 have usable general schedules and 123 remain unknown. Many merchant records carry September 2025 update dates; retrieval in November 2026 does not mean their hours were updated then. Denny’s branch addresses, hours and exact place-marker coordinates come from its official directions links. Ambiguous/inconsistent directions are excluded, including the NAIA Terminal 2 link pointing to Terminal 3. Only factual branch fields are bundled, not source-page HTML.

The API evaluates schedules in each venue's timezone at request time. The UI says **Open per published hours**, not confirmed live opening. Exceptional closures, menu availability and dietary suitability need confirmation with the restaurant. Each meal filters the area data against reviewed official menu items in `lib/restaurant-menu-matches.mjs`, not cuisine alone. No unrelated nearby restaurant is used as a fallback. Cards show the related item and its source link, explicitly labeled **Similar menu item**; this does not establish an exact recipe or diabetic suitability. If no primary menu match is open, `lib/similar-dining-meals.mjs` proposes a bounded set of related meals, using the original ingredients, preparation and format. The second pass checks those keys against reviewed menus at currently open nearby venues. It preserves the main ingredient and ranks similarity before distance and displays **Suggested meal**, **Why similar** and **What changes**. It never replaces the saved meal automatically or treats a similarity score as a nutrition/suitability score. If both passes fail, the message lists the similar ideas checked; unrelated nearby restaurants remain excluded. Unknown/closed restaurants are never presented as open options.

One location request serves all meals. Each planner timeslot has one restaurant section shared by its original meal and alternatives. Selecting an alternative or another planned meal immediately clears the old restaurant response, requests fresh hours with the existing location/radius, and filters results against the new recipe’s menu matches. The selected meal appears in the restaurant section and its Maps query. One area lookup is shared, while each meal has a separately computed list and menu reason; the app never falls back to the full area list. Older in-flight responses cannot replace the latest results. A meal change does not prompt for GPS or start a search before location/area opt-in. Nearby names may remain the same when they are still the matching or closest available options; exact dish availability is not inferred. GPS starts from the user's action; an already granted site permission is reused at startup. Choosing an area uses its explicitly labeled public anchor and never requests GPS. Coordinates, area selection and restaurant responses stay out of localStorage, cloud meal payloads and offline archives. Responses are private/no-store, expire after five minutes and clear offline.

## Reviewed menu sources

Menu facts were retrieved November 7, 2026 from the [official Denny’s Philippines PDF](https://dennys.ph/assets/pdf/Dennys_Menu.pdf) (rendered and reviewed, especially pages 3, 15, 19, 20, 26, 29 and 31) and [McDonald’s Philippines food pages](https://www.mcdonalds.com.ph/our-food). Only selected menu items are supported; no complete-menu coverage is claimed. For example, an omelette maps to Denny’s reviewed omelette item, seafood linguine maps to its shrimp pasta, and ice cream maps to reviewed dessert items. The second pass may relate chicken tinola to chicken arroz caldo or an oat-yogurt cup to a yogurt/berry/granola bowl. It must not turn fish into chicken, tofu into eggs, or a soy pudding into dairy yogurt just to fit a sparse menu. Fish suggestions preserve the preparation where known and try the original fish, bangus, tilapia and lapu-lapu; these are search ideas until a supported restaurant menu match exists. Currently no fish item in the saved two-chain menu catalog supports those suggestions, so no restaurant is asserted to serve them. Empty results explicitly apply only to the limited directory and link to broader Maps searches for each idea. Explicit dietary exclusions still apply. Breakfast-only McDonald’s items remain excluded because current service windows are not established.

## Optional live opening data

The owner can configure a restricted server-only `GOOGLE_PLACES_API_KEY` (or `GOOGLE_MAPS_API_KEY`), enable Places API (New), review billing/quotas and redeploy. This change creates no key or paid account. Never put keys in client code or chat. Google Text Search (New) requests only displayed fields, explicitly open and operational restaurants within the selected radius. Its general area results still require an independently supported menu match before appearing beside a meal; a cuisine or provider ranking alone is insufficient. Google results remain in active memory, show provider attribution and refresh only on user action. A failure or empty result falls back to the official directory where covered. The failing public Overpass service is no longer the default provider.
